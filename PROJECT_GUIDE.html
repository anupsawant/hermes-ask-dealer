Gideon Developer Guide

How the Gideon (Ask Dealer) fork of Nous Research's hermes-agent is built: the processes, the flows between them, where each piece of code lives, the packages it depends on, and what to edit when you want to change something.

01What this project is

Hermes Agent is an open-source personal AI agent by Nous Research. One Python agent core runs behind several surfaces: a terminal CLI, an Ink terminal UI (TUI), an Electron desktop app, a browser dashboard, and a messaging gateway that connects the agent to Telegram, Discord, Slack, WhatsApp and about 20 other platforms. It remembers across sessions (memory and skills), runs tools (terminal, files, browser, web search, code execution), delegates to subagents, and runs scheduled jobs.

This repository is a fork rebranded as Gideon, "Acme Corp's private AI assistant", for the Ask Dealer product. The product being built is the desktop app (apps/desktop). It spawns the upstream Python backend (hermes serve) as a child process and talks to it over HTTP and WebSocket.

What the fork changes

User-facing identity strings (Gideon, Acme Corp), the PDF skill (designed reports and a dealership daily-report template), and a placeholder login screen plus endpoint setup popup in the desktop app.

What the fork keeps

Everything internal: Python module names (hermes_*), environment variables (HERMES_*), the hermes CLI, IPC channel names (hermes:*). Rebrand only what users read.

Where most work happens

apps/desktop (Electron + React). The Python agent, gateway and TUI are upstream code that the desktop runs.

Design spec in progress

ASK_DEALER_LOGIN.md at the root: Google sign-in, a build-time "dealer edition" that hides advanced features, and a top-level endpoint setup.

How to read this guide

Sections 05–12 explain the runtime flows end to end. Sections 13–27 go component by component with file paths and key symbols. Sections 28–35 are reference tables. Paths are relative to the repo root unless they start with src/ or electron/, which are under apps/desktop/.

04Rules you must not break

These come from the root and area AGENTS.md files. Reviews reject changes that break them, and most of the architecture exists to protect them.

Prompt caching is sacred

Never change the system prompt, toolsets, memory snapshot or past messages mid-conversation. Providers cache the exact prefix bytes; a change re-bills the whole history. The only exception is context compression. Commands that would change prompt state apply to the next session (or take an opt-in --now).

The core is a narrow waist

Every core tool is sent on every API call. New capability arrives as a CLI command + skill, a service-gated tool, or a plugin, not as a new core tool. Order of preference: extend existing code → CLI + skill → gated tool → plugin → MCP server → core tool.

Never hardcode ~/.hermes

Use get_hermes_home() for paths and display_hermes_home() for text. On Windows the default is %LOCALAPPDATA%\hermes.

One process, many profiles

Code that runs outside a turn (timers, callbacks, RPC handlers, threads) must bind the owning profile explicitly. os.environ and module globals hold the launch profile's values; an unbound read leaks the default profile.

.env is secrets only

Behaviour settings go in config.yaml. Don't add new HERMES_* env vars for non-secret config.

Size and complexity ratchets

New functions: cyclomatic complexity ≤ 20, ≤ 300 lines, nesting ≤ 6. Files ≤ 2,000 lines. Units already over may only shrink. Enforced by python scripts/check.

Desktop seams

The renderer never touches Node or Electron directly; native power arrives as a typed preload capability. State lives with its authority: backend > Electron > renderer.

Tests are behaviour contracts

Use scripts/run_tests.sh, never bare pytest. No snapshot or source-reading tests. Tests never write to the real home. A fix ships with 1–2 tests proven red on the base.

Dependencies are bounded

>=floor,<next_major; git URLs and Actions pinned to a SHA. After editing pyproject.toml, run hermes pm lock and commit uv.lock. Never raw pip/uv into a Hermes env.

Guest content never opens anything

Artifact iframes and the preview webview can't open windows or the OS browser by themselves (security advisory GHSA-9f4c-93c8-jc8g). Don't widen setWindowOpenHandler, the preview partition, or the scheme allowlist.

05System architecture

Several front ends share one agent core. The desktop app, the TUI and the dashboard reach it through the same JSON-RPC backend (tui_gateway); messaging platforms reach it through the messaging gateway. Everything persists to the active profile's home folder.

The four seams

  1. Renderer ↔ Electron: only through window.hermesDesktop from electron/preload.ts. Windows run with contextIsolation: true, sandbox: true, nodeIntegration: false.
  2. Renderer ↔ backend (JSON-RPC): WebSocket ws://127.0.0.1:<port>/api/ws?token=… through JsonRpcGatewayClient (apps/shared/src/json-rpc-gateway.ts). Electron supplies the URL.
  3. Renderer ↔ backend (REST): proxied through Electron. hermesApi() → window.hermesDesktop.api() → IPC hermes:api → main picks the right backend by profile and connection.
  4. Electron ↔ backend: spawn args and env; readiness via the stdout line HERMES_BACKEND_READY port=N, then health polling.

06Desktop boot flow

Step by step

  1. electron/entry.ts (Linux only: may relaunch through WSLg/Wayland), then import('./main').
  2. Identity: applyDesktopIdentity(app) (main.ts:731) from electron/product-identity.ts. The identity is baked at build time as __HERMES_PRODUCT_IDENTITY__ by scripts/bundle-electron-main.mjs; dev reads product-identity.cjs live.
  3. Single-instance lock (acquireSingleInstanceLock, main.ts:1261). A second instance forwards deep links to the first and exits.
  4. app.whenReady() (main.ts:19318): login-shell PATH, system CA trust, safeStorage, secret migration, media protocol, hermes:// deep links, preview guest preload, tray, Quick Entry chord, application menu.
  5. createWindow() (main.ts:15021): frameless window with titleBarOverlay, loads the renderer, and starts the backend in parallel (main.ts:15471). The promise is shared through backendConnectionState so the renderer's getConnection() joins it.
  6. Backend resolution ladder (resolveHermesBackend, main.ts:5240): bundled payload → HERMES_DESKTOP_HERMES_ROOT (dev checkout) → source checkout when unpackaged → HERMES_DESKTOP_HERMES override → active install (%LOCALAPPDATA%\hermes\hermes-agent) → published launcher → otherwise bootstrap-needed (first-run installer, bootstrap-runner.ts).
  7. Spawn: serveBackendArgs (electron/backend-command.ts) builds [--profile X] serve --host 127.0.0.1 --port 0; only runtimes that lack serve get the legacy dashboard --no-open. Env: HERMES_HOME, a fresh 32-byte HERMES_DASHBOARD_SESSION_TOKEN, HERMES_DESKTOP=1, parent-watchdog identity.
  8. Readiness: the port announcement listener is attached before any await (90 s timeout), then waitForHermes health-polls (180 s budget).
  9. Renderer: useGatewayBoot calls getConnection(), opens the socket (8 attempts, 3 s apart, re-minting the URL each time), and publishes $connection / $gatewayState.

Extra backends (the pool)

The primary backend serves the launch profile. Other profiles get pooled backends: ensureBackend(profile) (main.ts:10939) reuses or spawns one, with LRU eviction. Limits come from pool-limits.json in userData. Local profile backends are never idle-reaped (upstream commit 167e9fdb84). Remote sources (SSH, URL+token, Cloud) go through ensureRegistryBackend(connectionId, profile). The serve process dies with the app; a messaging gateway started from it is detached and keeps running.

10Messaging gateway flow

The messaging gateway (hermes gateway run) connects the agent to chat platforms. It runs independently of the desktop and keeps running when the app closes.

  • Files: gateway/run.py (GatewayRunner, ~20 mixins), run_inbound.py (_handle_message), run_turn.py, run_busy.py, session.py (build_session_key), stream_consumer.py, platforms/base.py.
  • Session key: <ns>:<platform>:<chat_type>[:scope][:chat_id][:thread][:user].
  • Token locks: gateway.status.acquire_scoped_lock() stops two profiles from using one bot credential.
  • Platforms: built-in in gateway/platforms/ (api_server, webhook, signal, bluebubbles, weixin, whatsapp_cloud, …) and as plugins in plugins/platforms/ (telegram, discord, slack, whatsapp, matrix, teams, google_chat, email, sms, …).
  • Adding a platform: prefer the plugin path: plugins/platforms/<name>/plugin.yaml + adapter.py subclassing BasePlatformAdapter and calling ctx.register_platform(). Guide: gateway/platforms/ADDING_A_PLATFORM.md.
  • Gateway session hygiene compresses at a fixed 85% of the window before the agent runs.

11Scheduled jobs (cron)

  1. Create: via CLI hermes cron, the /cron command, the cronjob_manage tool, or REST /api/cron/*. Jobs are stored in <HERMES_HOME>/cron/jobs.json (cron/jobs.py::create_job).
  2. Schedule syntax (parse_schedule): 30m, every 2h, every monday 9am, 5-field cron, or an ISO timestamp for one-shots.
  3. Tick: cron/scheduler_tick.py::tick() advances next_run_at before dispatching. One ticker iterates every served profile.
  4. Where it runs: inside the messaging gateway, or inside the desktop's serve backend when HERMES_DESKTOP=1 (unless a gateway already owns that profile).
  5. Run: an agent turn with skip_memory=True; inactivity watchdog 600 s; output under cron/output/; delivery to the origin chat or locally.

Kanban (hermes_cli/kanban*.py, SQLite) is a task board whose dispatcher runs in the gateway every 60 s; tasks auto-block after kanban.failure_limit failures (default 2).

14System prompt & caching

Assembly: agent/system_prompt.py::build_system_prompt_parts. Content and loaders: agent/prompt_builder.py. The prompt is built in three tiers, ordered from most to least stable so the cacheable prefix is as long as possible.

TierContents
StableIdentity (SOUL.md from the profile home, else DEFAULT_AGENT_IDENTITY), agent-help guidance, model/tool guidance (gated per model family), auto-loaded pinned skills.
ContextCaller's system_message, project context files, worktree snapshot, workspace guidance, platform hints.
VolatileSkills index (first), MEMORY.md/USER.md snapshot, external memory block, plugin prompt sections, active-profile line, timestamp, runtime-environment block.

The built prompt is cached on the agent and persisted to sessions.system_prompt. Each later turn restores it byte-for-byte when the runtime still matches, which is what keeps the provider's prefix cache warm.

Project context files

build_context_files_prompt loads one type; the first match wins:

  1. .hermes.md / HERMES.md (nearest, walking up to the git root)
  2. The AGENTS.md chain from git root down to cwd (AGENTS.override.md wins per directory)
  3. CLAUDE.md (cwd only)
  4. .cursorrules + .cursor/rules/*.mdc (cwd only)

Each file is security-scanned and capped at 20,000 chars (or 6% of the context window, up to 500K; context_file_max_chars overrides). Subdirectory AGENTS.md files found later are appended to tool results (agent/subdirectory_hints.py), never to the system prompt.

What may change mid-conversation

Never

  • System prompt bytes
  • Toolsets
  • Memory snapshot
  • Past messages
  • Two same-role messages in a row

Allowed channels

  • Skill slash commands inject a user message
  • pre_llm_call plugin context and memory prefetch ride the current user message (api_content sidecar)
  • Surface-switch notes on the user channel
  • Prefills added at API-call time only

Memory written mid-session goes to disk but doesn't change the prompt until the next session. The prompt is rebuilt only after compression (invalidate_system_prompt).

Anthropic prompt caching

agent/prompt_caching.py places four cache_control breakpoints: after the static prefix, at the end of the system prompt, and on the last two messages. TTL from prompt_caching.cache_ttl (5m default, 1h, or auto). A rotation-stable prompt_cache_key comes from agent/prompt_cache_scope.py.

15Context compression

When it triggers

  1. Turn start: optional idle compaction (idle_compact_after_seconds), then a preflight threshold check.
  2. Before each API call (run_preflight_gate).
  3. After tool results (compress_after_tool_results).
  4. Provider overflow / 413 (turn_overflow, up to max_compression_attempts = 3).
  5. Manual /compress.
  6. Gateway session hygiene at 85%.

Thresholds

compression.threshold defaults to 0.50 of the main model's window; windows under 512K are floored at 0.75. Overrides: threshold_tokens, model_thresholds (substring match). Token counts come from the usage anchor (real provider usage plus an estimate of the delta).

What compress() does (agent/context_compressor.py)

  1. Prune old tool outputs (>200 chars, outside the tail) to placeholders. No LLM call.
  2. Pick boundaries: protect the head, keep a token-budget tail (tail_mode: lean, protect_last_n 20), never split a tool call from its result.
  3. Summarize the middle with the auxiliary compression model into Goal / Constraints / Progress / Decisions / Files / Next Steps / Critical Context. Later compactions update the previous summary.
  4. Assemble head + summary + tail; repair orphaned tool pairs; rebuild the system prompt (the one sanctioned cache break).

With compression.in_place: true (default) the session id stays the same; old rows are soft-archived (active=0, compacted=1). Failures back off 60 s → 300 s → 900 s. A different engine can be plugged in through context.engine and plugins/context_engine/.

35Glossary

HERMES_HOME
The active profile's data folder (config, secrets, state.db, skills, memories, logs).
Profile
An isolated home under profiles/<name>/. Profiles are islands on purpose. A Bot Mode bot is a profile.
Multiplex
One process (gateway or serve) serving several profiles, binding the right home per activity.
Turn
One user message through to a final answer, including every model call and tool round.
Toolset
A named group of tools enabled together; the model only sees tools a toolset names.
check_fn
A tool's availability check (credentials present, opted in) for the current profile.
Auxiliary model
A side LLM for tasks like compression, titles, vision and approval judgement, configured under auxiliary.<task>.
Compression
Summarizing the middle of a long conversation to fit the context window; the only allowed prompt-cache break.
SOUL.md
The persona file. When present in the profile home it replaces the default identity.
Skill
A folder with SKILL.md and optional scripts and templates that teaches the agent a procedure.
Server request
A question from the backend to the client mid-turn (approval, clarify, secret), which blocks the agent until answered.
Facade + siblings
Code layout: a thin module keeps public names; <stem>_<topic>.py files hold the logic.
Contribution
A registration (pane, route, nav item, keybind, palette entry) in the desktop's contribution registry.
Pool backend
An extra hermes serve process the desktop spawns for a non-primary profile or connection.
Variant / edition
Variant (HERMES_DESKTOP_VARIANT) is packaging identity: Gideon, Light, Bundled, Store. Edition (planned) is dealer vs full feature set.
Canonical Bot Chat
A bot's single forever-chat, identified by the session title Bot Chat within its profile.
